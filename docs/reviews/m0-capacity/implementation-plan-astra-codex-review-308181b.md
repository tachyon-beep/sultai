## Blocking items

### B1. The interval contract is not reproducible yet

Task 13 calls `paired_bound` a bootstrap bound “using `fit.paired_se`,” but that function returns only the standard deviation of bootstrapped means, not bootstrap quantiles (`docs/plans/2026-10-13-m0-implementation.md:313`; `src/sultai_screen/fit.py:247-256`). A normal bound, mean ± 1.645 SE, and a percentile bound can differ; the plan also leaves median convention, quantile interpolation, sign-test inversion/ties, and achieved half-width undefined. Its `AnchorResult` description does not require aligned per-example vectors, although the frozen protocol requires paired endpoint uncertainty for loss and accuracy (`docs/plans/2026-10-13-capacity-frontier-screen.md:325-366`).

**Fix:** Specify the per-example interval construction separately from the required percentile anchor-bootstrap, retain aligned loss/correctness vectors, and state the median, quantile, sample-SD and half-width conventions. Define the exact sign-test bound as a confidence bound on the population median, including ties and insufficient sample size, and test numerical reference cases rather than merely “positive sample” inequalities. Preserve 10,000 resamples and the frozen anchor-level verdict rules.

### B2. The frontier task does not implement the full frontier quantity

Task 13 names least squares and a seed-bootstrap slope, but `gain_fraction_of_doubling(gain, slope) -> float` cannot produce the required fraction interval, and no task explicitly constructs the second descriptive fit when optional widths run (`docs/plans/2026-10-13-m0-implementation.md:313-315`; `docs/plans/2026-10-13-capacity-frontier-screen.md:354-361`). The slope sign and resampling unit are unstated: loss ordinarily declines with log2 parameters, while “gain per doubling” should use the negative fitted loss slope. **[derived]** Resampling the three width points themselves estimates uncertainty in the chosen design; it does not estimate seed-to-seed uncertainty at the fixed widths.

**Fix:** Define the fitted response, slope sign, aggregation at each width, and independent within-width seed resampling for the disjoint seed blocks. Jointly bootstrap the reference module gain and slope, preserving their shared reference-host observations, to obtain the fraction interval; explicitly report an unavailable/unbounded scale when the denominator is unsuitable. Add the optional all-10-epoch-width fit, the required label and the exclusion of the cooled point, with no extrapolation.

### B3. The slicing interfaces cannot perform the prescribed mean fold

The frozen cut needs activation means on the fit examples (`docs/plans/2026-10-13-capacity-frontier-screen.md:190-196`). Task 7's `cut(adapter, keep)` and `random_cut(adapter, h, seed)` receive neither fit features nor activation means, so the random cut cannot implement the same fold; Task 8's residual interface likewise receives neither the fitted adapter nor its precomputed losses (`docs/plans/2026-10-13-m0-implementation.md:237,249`). **[derived]** The zero-column known-answer fixture does not expose this omission: every removed contribution is zero, regardless of whether its mean was computed.

**Fix:** Pass fit features or explicitly computed fit activation means to every folded-cut path, and pass the fitted adapter or its aligned losses to residual evaluation. Add a nonzero-removed-unit fixture that verifies the bias update against an independent calculation, alongside the existing zero-column and wrong-survivor controls. Specify deterministic tie-breaking and record survivor indices for contribution, random and ablation rankings.

### B4. S-static's trained module and refit are not given an executable scientific contract

Task 11 trains and exposes a static adapter, but Task 16 does not specify saving/loading its learned W and b, and its module-action list omits the static and finished-host refits (`docs/plans/2026-10-13-m0-implementation.md:288-290,350`). The current `Host` forward has no module and `state_hash(host)` covers only that host's parameters and buffers, so an inner-host checkpoint/hash cannot establish the trained static model's identity (`src/sultai_screen/host.py:74-95`). **[derived]** Dropping the learned module, replacing it with a fresh module, warming the same module, and adding a second module are different D5 experiments; only an explicit interpretation of “refitted” makes the frozen comparison reproducible (`docs/plans/2026-10-13-capacity-frontier-screen.md:292,342-345`).

**Fix:** Define static serialization and a hash covering the host plus learned module, and evaluate the complete static model before refitting. State explicitly how the existing trained module is refitted on the frozen inner host—retaining it and using its tensors as the warm start is the natural reading—and include that path and M-sq | T-cool in the worker roster. Test the no-refit and refit D5 values against complete-model forwards, including the correct evaluation baseline.

### B5. N0 and post-fit recalibration need state and cache boundaries

Task 9's `no_op` accepts selection `Features`, while R-bn changes front BatchNorm buffers; cached site tensors from the raw host are therefore not valid for evaluating the recalibrated host (`docs/plans/2026-10-13-m0-implementation.md:264-266`; `src/sultai_screen/host.py:224-232`). Task 16 publishes the chosen host hash but does not define the chosen-state handoff, and Task 10 keeps BatchNorm statistics frozen without specifying R-all's required post-fit recalibration (`docs/plans/2026-10-13-m0-implementation.md:276,350`; `docs/plans/2026-10-13-capacity-frontier-screen.md:215-222,311-313`). Its complement hash includes buffers, so checking it across R-all's deliberate recalibration would also conflate a permitted calibration change with a re-tuning defect.

**Fix:** Evaluate each no-op candidate using features recomputed from that candidate, save/bind the selected N0 state, and make subsequent arms consume that state; apply the finished host's own N0 rule before its module fit. Specify R-all's recalibration and selection/evaluation order, with the re-tune complement invariant checked before that separately recorded calibration operation. Add tests where front BatchNorm recalibration materially changes cached features and where a downstream arm would fail if it loaded the raw host instead of N0.

### B6. Several required reports have no concrete producing task

HARM is pinned but no task applies the inherited raw-candidate harm screen; Task 13 also omits the explicit re-tune fraction, unfolded-slice report, leave-one-out ceiling report, and separate strict random-rank contrast (`docs/plans/2026-10-13-m0-implementation.md:23,237,313,350`). The broad “every module-grid arm” description also needs an exception for h = 16, 4, 2, whose refit is one 800-step run at the selected M-wide rate, not the full grid (`docs/plans/2026-10-13-m0-implementation.md:350`; `docs/plans/2026-10-13-capacity-frontier-screen.md:289`).

**Fix:** Add an explicit report schema and producer/test for every listed descriptive quantity and the raw-candidate harm inventory, retaining numerical failures without using dev to reselect candidates. Name both random D2 and random D2s, unfolded losses, ablation-ceiling cuts, survival curves and R-all fractions, with explicit undefined-ratio handling. Give the smaller survival-curve refits their frozen single-rate/800-step execution rule and book those runs.

### B7. Pilot-filled schedules and measured cost projection are incomplete

The protocol permits raising the schedule axis and requires projections from measured one-per-card maxima (`docs/plans/2026-10-13-capacity-frontier-screen.md:234-240,502-503,529-531`). **Fix:** Add a reviewed schedule-fill receipt and propagation contract, decided before development medians and preserving matched optimiser steps/example passes between the two D2 routes. Build pilot and confirmatory projections from explicit measured workloads, including measured static training/refit cost and the fixed V0 workload, rather than a literal +110. Define whether the admission projection is total or remaining work so already charged stages are counted exactly once, and test the integrated core-over-ceiling hold before any V1 publication.

### B8. The P1 fallback silently changes the frozen validation case

**Fix:** Pin the verdict-bearing B3/A3 comparison to alpha = 0.1 and test that materiality diagnostics cannot replace it. If that fixed case is unusable, publish an instrument hold; any replacement is an amendment-2 candidate, not a pilot fill.

### B9. The complete launcher and stop-receipt paths still need M0 binding

Task 17 says `stop_report` is reused, but the existing function explicitly expands Gate 3's `protocol_identity()` (`docs/plans/2026-10-13-m0-implementation.md:363`; `src/sultai_screen/pilot.py:369-387`). In addition, Task 18 requires `static_admitted` but Task 17 does not explicitly publish that SD-based decision, and the optimizer file lacks a stated receipt hash binding like the existing host and loss-stream bindings (`docs/plans/2026-10-13-m0-implementation.md:350,363-375`; `src/sultai_screen/screen.py:135-142`).

**Fix:** Provide M0-specific stop envelopes, explicit M0 supervisor arguments, and pilot/confirmatory arm whitelists, with failed-path identity and exclusion tests. ### B10. CPU golden tests do not discharge the new GPU equality claims

The plan explicitly requires GPU host replay but gives CPU tests for resumed momentum training, checkpointed fits, affine folding and the logits/losses refactor, without a corresponding GPU acceptance matrix (`docs/plans/2026-10-13-m0-implementation.md:27,175-177,199-200,216-228,254,363-365`). Existing tests deliberately simulate batch-shape-sensitive GPU behavior, and the current loss evaluator computes cross-entropy inside each padded chunk, not on concatenated logits (`tests/test_fixed_evaluation.py:18-25,103-135`; `src/sultai_screen/fit.py:64-70`). **[derived]** Moving cross-entropy outside that loop, changing the checkpoint evaluation workload, or restoring momentum incorrectly can preserve a CPU golden value while changing GPU results.

**Fix:** State which assertions are mathematical/tolerance claims and which require bitwise equality, then add pilot GPU checks on both pinned cards for resume versus uninterrupted training, checkpoint versus separate-fit prefixes, complete static step-zero identity, and shared padded logits/losses/correctness evaluation. Keep cross-entropy's padded chunk shape unchanged and validate the selected affine fold's endpoint residual on GPU; do not turn mathematical interior equality into a bitwise floating-point claim. Complete these checks and record their costs before the affected scientific readings.

## Non-blocking notes

Describe it that way. It is a conventional discretization, not a scientific blocker.

**N2. Unaugmented normalized images are sound for the adaptation controls.** Cached module features already come from normalized, unaugmented images; using the same views for R-aff and R-all avoids giving those controls a different adaptation-data regime (`src/sultai_screen/host.py:224-232`; `src/sultai_screen/data.py:143-146`; `docs/plans/2026-10-13-m0-implementation.md:276`). This is conditional on B5's state/cache discipline.

**N3. Not reopening Simic terminal receipts is scientifically defensible.** The published Attempt-4 admission records both terminal hashes, 768 units each and the owner release; the plan retains fresh pinned-card/idle checks (`docs/results/gate3-pilot-2026-10-13-linked-3/admission.json:1`; `docs/plans/2026-10-13-m0-implementation.md:363`). The separate pilot go and fresh resource checks remain necessary; I did not verify current external ownership.

**N4. Six 0.5-host anchors and new test modules are sound.** Six anchors are explicitly named in the frozen extended arm, not merely an optional plan interpretation (`docs/plans/2026-10-13-capacity-frontier-screen.md:300-308`); they support a descriptive screen, not a starved-host confirmation. New M0 tests preserve the published Gate 3 identity chain while testing the carved-out path, consistent with retaining Gate 3 workers (`docs/plans/2026-10-13-capacity-frontier-screen.md:119-139`; `docs/plans/2026-10-13-m0-implementation.md:28-29,304`). **N5. The seen-fit derivation and momentum representation are sound choices.** The fixed permutation selects a host-independent 2,000-example subset of the existing 40,000 indices, and the existing generator derivation is explicit (`docs/plans/2026-10-13-m0-implementation.md:197-199`; `src/sultai_screen/data.py:104-121`; `src/sultai_screen/contracts.py:82-90`). All host parameters are updated by the existing fixed-recipe SGD, so saving every named momentum buffer and reconstructing the fixed groups is sufficient at an epoch boundary when global epoch labels are retained (`src/sultai_screen/host.py:133-168`; `docs/plans/2026-10-13-m0-implementation.md:166,185`). Binding the bytes and checking GPU resume remain B9/B10; I did not compute the future SEEN_FIT_SHA.

**N6. Static zero initialization preserves the initial host, not its later trajectory.** Creating zero W and b after `make_host`, without random draws, preserves the host initialization and named data streams (`docs/plans/2026-10-13-m0-implementation.md:288-290`; `src/sultai_screen/host.py:81-86,152-154`). **[derived]** W can receive a nonzero first gradient at W = 0, while the module initially forwards identity, so subsequent training should differ. This is the correct static-capacity control; it does not settle B4's refit/storage contract.

**N7. The inherited sizing rule and pure verdict branches are faithful.** `anchor_count` returns `(n*, max(32,n*))`, with `n* = ceil((1.645 × 1.25 × SD(D1)/(X/2))²)`; the plan's examples give 32 at SD = 0.0275 and 39 at SD = 0.03 (`src/sultai_screen/contracts.py:182-186`; `docs/plans/2026-10-13-m0-implementation.md:313-315`). The V1/V2 inequalities and directional certification guards match the frozen rules (`docs/plans/2026-10-13-m0-implementation.md:325-327`; `docs/plans/2026-10-13-capacity-frontier-screen.md:385-424`). **[derived]** The 1.25 factor approximates the normal-population median's SD inflation; it is an approximation, not a guaranteed achieved bootstrap width.

**N8. Small-n percentile intervals are implementable but coarse.** The frozen percentile bootstrap is appropriate to implement as specified, including at n = 6; six-anchor readings remain descriptive (`docs/plans/2026-10-13-capacity-frontier-screen.md:363-366,507,527`). **[derived]** Exact one-sided median bounds from binomial inversion use order statistics 1 and 6 at n = 6 (coverage 98.4375%) and 11 and 22 at n = 32 (coverage about 97.495% for a continuous population). These are confidence bounds on the median, not Clopper–Pearson bounds on the proportion of positive anchors; percentile-bootstrap bounds need not coincide with them.

## Answers to Questions 1–7

**1. Complete implementation of the frozen study? No, not yet.** The §2 new-code categories all have named task homes: host/recipe/seed/state work in Tasks 2–4/16, fitting/calibration/re-tuning/slicing/accuracy in Tasks 5–11, instrument carve-out in Task 12, and supervision/statistics/reviews in Tasks 13–19 (`docs/plans/2026-10-13-m0-implementation.md:105-387`). Unsupported additions/readings are the alpha fallback (B8), an unrestricted module roster at confirmation (B9), and omission of co-tenancy (A1); a full grid for smaller survival-curve refits would also add unregistered behavior (B6).

**2. Scientific validity of the plan's own decisions? Mostly sound, conditionally.** Per-step cooling and the 20-epoch point are sound with N1's endpoint wording; unaugmented adaptation/recalibration is sound subject to B5; historical Simic receipt reuse is defensible subject to fresh permission/resources (N3). Six starved-host anchors and separate tests are sound (N4), the seen-fit derivation is sound (N5), the named momentum-buffer contract is sufficient in principle (N5, B9/B10), and static zero initialization preserves the step-zero host in principle (N6), while complete static execution/refitting remains blocked by B4. **3. Statistics? The broad rules match; the numerical implementation is under-specified.** Percentile bootstrapping of the median over anchors, exact sign-test bounds at confirmation, D1-only sizing with the inherited formula, and a fixed-three-width seed-bootstrap frontier are consistent with §6/§9 (`docs/plans/2026-10-13-capacity-frontier-screen.md:354-366,521-526`). **4. Bitwise/determinism claims? Plausible structurally, not verified on the new GPU path.** Replacing only tail-width literals can preserve the reference constructor's names and random draws; copying the training loop can preserve the original recipe (`src/sultai_screen/host.py:56-86,129-177`; `docs/plans/2026-10-13-m0-implementation.md:155,185`). The existing fitter's seed-derived order has identical prefixes and loss evaluation draws no RNG, supporting checkpoint equality in principle (`src/sultai_screen/fit.py:55-75,185-197`). Folding is an algebraic equality in the interior with floating-point tolerance and a real border residual, while padded evaluation preserves kernel shape rather than proving arbitrary GPU implementations bitwise (`docs/plans/2026-10-13-m0-implementation.md:251-254`; `tests/test_fixed_evaluation.py:103-135`). All new runtime equality claims need B10's GPU checks; the plan currently says so explicitly only for host replay.

**5. Costs and ceilings? Correct stated ceilings and admission order, incomplete measurement contract.** Task 15 carries 14,400 / 43,200 / 50,400 seconds, stops at the first extended miss, and names a core-over-ceiling stop before V1; Task 17 places projection/admission at stage 4 (`docs/plans/2026-10-13-m0-implementation.md:338-340,363`). Those match §8/§10, and the corrected static arithmetic is sound: 33,820 seconds without static and 37,340 with the illustrative static cost; 14 hours is a protocol condition, not a claim that 37,340 exceeds 12 hours (`docs/plans/2026-10-13-capacity-frontier-screen.md:476-503,538-548`). B7 requires measured costs and an integrated stop; B9 requires the correct confirmatory worker and explicit owner ceiling authorization. CPU mocks cannot establish the future charged GPU cost.

**6. Co-tenancy amendment candidate? Agree, with A1's qualification.** Simultaneous use of different cards does not reproduce the existing same-card co-tenancy stress check. An exception or deletion requires owner disposition; neither follows automatically from a booking being conservative.

**7. Anything else to block before code?
