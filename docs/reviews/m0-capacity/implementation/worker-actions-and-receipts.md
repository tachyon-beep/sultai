## Findings

**I-1 (Important, tests). The worker shell's custody guarantees are unpinned.** `tests/test_m0_worker.py:153-164`, `worker.py:1304-1306, 1322-1329`. `patched()` replaces `install_seal` and `configure` with `return_value` mocks, and no test runs a child into an existing output or raises an instrument-class error through `worker()`. Mutant B (seal installed after `load_dataset`, `configure(cuda=False)`, `exist_ok=True`, and every failure classed `software_valid=False`) gave `Ran 29 tests … OK` on `test_m0_worker` + `test_m0_supervision`, so every sub-change survived. Why it matters: these are §2 "carried over unchanged" custody properties (data seal, one pinned card, no reuse of an output) and the Supervisor's instrument-versus-software split (`pilot.py:239`). Today the source is right only because it copies `screen.worker` line for line. Fix: add a test that asserts the mock call order (`install_seal` before `configure`, `mkdir` and `load_dataset`) and `configure` called with `cuda=True`; a second child into the same `--output` must raise `FileExistsError` with no receipt written; an action patched to raise `InstrumentHold` (and `OracleUnavailable` with candidates) must publish `software_valid=True`, `instrument_valid=False` and `unavailable_candidates`.

**I-2 (Important, tests). No test shows that a file changed after publication is refused.** `receipts.py:94-98, 132-137`; `worker.py:257-260`. Each test either checks that the published SHA equals the file or runs the happy path. Mutant A (`receipts.bound`, `receipts.load_vectors` and `worker._bound` all made no-ops) gave `Ran 65 tests … OK` on `test_m0_worker` + `test_m0_pilot`, so all three binders can be removed without a test failing. The SHA binding of `vectors.pt`, `host.pt`, `optimizer.pt`, `static-module.pt` and `loss-stream.bin` is a stated claim of this item, and it is what makes the per-example D vectors trustworthy. Fix: one test per binder. Rewrite a byte of `vectors.pt` (and of `host.pt`/`optimizer.pt` for `_bound`/`bound`) after publication, then expect `PilotHold("…unbound or changed after publication")` from `receipts.source`, `receipts.bound` and `worker.load_training`; a missing bound file must also hold.

**I-3 (Important, tests). The rate-set routing is invisible to the fixture.** `tests/test_m0_worker.py:168-169` patches `MODULE_RATES` and `RETUNE_RATES` to the same `(0.1,)`. Swapping the frozen grids between arms therefore produces identical receipts: M-aff on the three-rate module grid (against the [J-route] five-rate grid), re-tune arms on module rates, or the h = 16/4/2 survival refit at a fixed rate instead of M-wide's selected rate. The assertion `arm["rate"] == wide_rate` (:460) is vacuous when the grid has one rate. Mutant C (`rate=MODULE_RATES[0]` in the survival refit) gave `Ran 1 test … OK` on `test_modules_runs_every_module_arm_with_vectors_harm_cuts_and_single_survival_refits`, so the mutant survived. Fix: patch distinct rate sets, e.g. `MODULE_RATES = (0.1, 0.05)` and `RETUNE_RATES = (0.2, 0.1, 0.03)`. Then assert that each arm's candidate rates equal the set it must use (M-aff, R-272s, R-aff and R-all the re-tune set; every other grid arm the module set) and that each survival refit's rate equals M-wide's selected rate, where a fixture or a patched selection makes that differ from `MODULE_RATES[0]`.

**I-4 (Important, tests). The GPU acceptance flags (i)-(iv) have no negative control.** `tests/test_m0_worker.py:564-585`. The test only asserts that each flag `is True` on a correct system. An `acceptance_action` that returned `True` constants would pass. Because these flags gate stage 1 on GPU (§9; a False is meant to stop the pilot), each needs a case where it must turn False. Fix: patch to break each comparison once. For example, make `_optimizer` return a fresh optimiser without momentum, or change one resumed epoch's rate (i → False); perturb one snapshot adapter or patch `fit_sgd` to shift the rate (ii → False); give `StaticHost` a nonzero module (iii → False); patch `losses` to add 1e-3 (iv → False).

**M-1 (Minor). `receipts.inventory` ignores `cause`.** `receipts.py:172-181`. A dependent arm recorded unavailable because M-wide failed (cause "M-wide", `worker.py:811`) carries M-wide's candidates, and `inventory` labels them as that dependent's own raw candidates. That is the misattribution the worker's `cause` field (docstring `:595-597`) exists to prevent. It is unreachable today, because M-wide is required wherever it runs (`PILOT_ARMS`, `CONFIRMATORY_ARMS`) and holds first, and the starved pair does not run it. Fix: list only candidates where `record["cause"] == name`, and give the others an empty inventory.

**M-2 (Minor). A selected candidate that is finite on selection but nonfinite on development fails the child instead of recording the arm unavailable.** `worker.py:640, 664, 682` evaluate with `losses(..., check_finite=True)`, which raises `PilotHold` (`fit.py:109-110`). `Collector.attempt` catches only `OracleUnavailable`, so the modules or retune child publishes `software_valid=False` and the pilot stops. This fails loudly and never zero-fills, which matches Gate 3, but it is not the R11 "anchor retained, arm unavailable" path. Fix: record the choice in the R11 ruling text, or route it through `OracleUnavailable` with the candidate report.

**M-3 (Minor). The accuracy half of acceptance (iv) is tautological.** `worker.py:1217-1220`. `fit.accuracy` is defined as `logits(...).argmax(1) == labels` (`fit.py:133-135`), so comparing it with `raw.argmax(1) == labels` from the same `logits` call cannot fail. The losses half (padded in-chunk cross-entropy against cross-entropy of the padded logits, within 1e-6) is the substantive check. Fix: compute the accuracy reference from an independent unpadded forward (`host.classify(development.base)`), as the plan's Task 5 test does, or say in the docstring that only the losses half can fail.

No behaviour outside the preregistration was found. There is no extra arm: the leave-one-out cut is §4 l.195-196's control. The worker adds no RNG draw: `_probe` keeps Gate 3's order of make_host, then probe, then train, and the zero-module check draws none. These files change no Gate 3 receipt byte: both are new files, and the Gate 3 workers are not imported, as `test_worker_imports_neither…` shows. `--width` and `--magnitudes` are accepted for Supervisor compatibility and are inert. No finding is BLOCKING: every frozen literal matches the preregistration. All four Important findings are test gaps in front of source that is correct today.
