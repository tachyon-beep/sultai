## Findings

**F1 — Important — `retune.py:352` (and the docstring at `:305-306`).**
*What:* `retune_grid` never applies the plateau rule. R-272s and R-aff therefore always carry `plateau_certified: None` (and the worker records `certified: None`, `worker.py:989`).
*Why:* The §4 oracle-grid paragraph covers the re-tune arms explicitly ("{1, 0.3, 0.1, 0.03, 0.01} for re-tune arms … One 3,200-step run per rate … Plateau is certified by the v4 Table B rule applied to the 800- versus 3,200-step checkpoints"). It then exempts only R-all ("R-all, run to 800 steps only, is never plateau-certified and enters no certification fraction"). That exemption only makes sense if the other re-tune arms are certified. §9 stage 5 asks for "plateau fractions per arm" over all core cases, and R-272s and R-aff are core. The source does less than the preregistration. The docstring's reason ("needs per-example traces the snapshot hashes do not carry") is also inaccurate: `RetuneCandidate.snapshot_hosts` keeps the frozen 800- and 3,200-step hosts, so per-example selection losses can be recomputed with `features_from_images`, and the final-checkpoint candidate carries all 3,200 training losses for the last two 40-step windows.
*Effect on verdicts:* none. §7 V1/V2 read certification only for M-aff, M-sq, M-small-B and the refit, so this is a reporting omission, not a verdict defect. The final branch review listed it under "declined to judge"; this review judges it against §4/§9.
*Fix:* mirror `fit.grid`. Take `early` = the best finite candidate at `checkpoints[-2]` and `late` = the best finite candidate at `checkpoints[-1]`. Apply the Table B arithmetic of `fit.plateau`, with the paired difference taken from `losses(early.host, features_from_images(early.host, …selection), None) − losses(late.host, …)` and the tail windows from `late.training_losses[-80:]`. Apply it only when the schedule has at least two checkpoints and the arm is not R-all (the caller can pass a flag, or R-all's 20-checkpoint 800-step axis can be detected explicitly). Then replace the `assertIsNone(result.plateau)` pin with a certified/uncertified reference case. This is a code change; no frozen value moves.

**F2 — Minor — `retune.py:355-377`, `recalibrate_after`.**
*What:* `dataclasses.replace` puts the post-recalibration host, state hash and selection on the returned candidate, but it keeps the pre-recalibration `snapshots`, `snapshot_hosts`, `training_losses` and `complement`.
*Why:* The report mixes two host states. The docstring declares the complement choice, and the worker records both hashes, so nothing is lost. This was already deferred under Task 10 and is noted only for completeness.
*Fix:* none required. Optionally, have `report()` label the snapshots as pre-recalibration when `pre_recalibration_hash` is set.

**F3 — Minor — `retune.py:79` / `tests/test_m0_retune.py:148-158`.**
*What:* No test pins that the complement hash covers BatchNorm buffers. Removing `("buffer", host.named_buffers())` from the hash leaves all 12 `RetuneTests` green (mutation M1).
*Why:* The V0 clause "the complement hash unchanged under every re-tune arm" is the guard against a BN running-statistics leak during fitting. A hash without buffers would pass V0 even if a fit ran in train mode. The current source is correct, and the buffer-equality assertions in `test_r272s_…`/`test_raff_…` check the fitting path directly, but they do not check the hash.
*Fix:* in `test_complement_hash_sees_only_the_complement`, perturb one `running_mean` entry on a copy and assert that the complement hash changes.

**F4 — Minor — `tests/test_m0_retune.py:50-51` (FIT = 32 examples).**
*What:* The multi-chunk minibatch stream (n = 2,000, so 8 chunks per permutation and a 208-example last batch) is not exercised. Drawing a fresh permutation on every step survives the suite (mutation M3).
*Why:* The plan requires `fit_sgd`'s stream, so that re-tune and module arms see the same example order. The source matches `fit.py:289-292` by reading, but no test would catch a divergence. Task 6 has the analogous deferred minor for `fit_sgd`.
*Fix:* add a fixture with more than 256 fit examples, and assert that 3 steps of `fit_retune` give the same per-step minibatch ids, and training losses on a matched cached site, as an independently computed permutation schedule.

**F5 — Minor — `tests/test_m0_retune.py:247-267`.**
*What:* Nothing pins that `recalibrate_after` recalibrates on the fit examples. Swapping in `selection_indices` survives the suite (mutation M2).
*Why:* §4 defines R-bn as "BatchNorm recalibration on the fit examples". Recalibrating on the selection split would leak selection data into R-all's host. The source is correct (`retune.py:369`).
*Fix:* assert that `recalibrated.host`'s buffers equal those of `recalibrate_bn(<unsealed copy of candidate.host>, data.images, FIT)`, and differ from the result on `SELECTION`.

Behaviour outside the preregistration (point 4): none of consequence. There are no extra arms. No extra randomness is introduced: `_copy` calls `make_host` under `torch.random.fork_rng` (`host.py:92-95`), and its init is overwritten by `load_state_dict(strict=True)`, so neither the global RNG nor the `oracle-order` stream is perturbed. There is no Gate 3 receipt or path change: the file is new, and it imports `fit._passes` and `fit.at_edge`/`losses` without modifying them. The nonfinite-candidate retention (`:217-232`, `:347-348`) is the inherited "anchor retained, arm unavailable" convention. The cached-site guard (`:180-181`) is a stricter refusal, not added behaviour.
