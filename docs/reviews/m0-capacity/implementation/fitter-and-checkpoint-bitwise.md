## Findings

**Important 1 — the 800-versus-3,200 comparator index is not pinned.** fit.py:513-514; tests/test_m0_fit.py:320, 389. Both grid tests use `checkpoints=(40, 80)`, where `checkpoints[-2] is checkpoints[0]`. Changing 513 to `checkpoints[0]` (plateau on 200 vs 3,200, which is not the preregistered comparator and is a far easier certification) passes every FitTests test. Why it matters: the certified fraction is a gate input (CERTIFIED_FRACTION 0.75). Fix: add one grid test with three checkpoints (e.g. (20, 40, 80)) asserting `plateau()` was computed on the 40- and 80-step bests (compare `result.selection_se` to `paired_se` of those two), and that the 20-step candidates do not enter it.

**Important 2 — the real post-divergence checkpoint path is exercised only through a mock, and it is not bitwise a separate run in its trace.** fit.py:298-313, 497-498; tests/test_m0_fit.py:366-395. When a run reaches a checkpoint and later diverges, `fit_sgd` returns `training_losses=()`, so grid gives the reached checkpoint candidate the correct snapshot and selection loss but an empty trace and, via `_passes`, the passes of a run that completed (correct), whereas a separate run of that length would have reported its full trace. Selection, choice and plateau are unaffected (plateau reads only the finite final checkpoint), so no verdict input changes; but the claim "bitwise the same as separate runs" holds for weights and loss only, and the only test of the path patches `fit_sgd`, which by the brief's rule pins nothing about the real code. Fix: either retain the trace prefix up to the last finite step on failure, or state in the receipt that a diverged run's earlier checkpoints carry no trace; and add a non-mock test that forces divergence (e.g. rate 1e6 on the fixture) after the first checkpoint and asserts the reached snapshot equals a separate run of that length.

**Minor 3 — the v4 pass count (seven 256 + one 208 over 2,000) is unpinned and duplicated.** fit.py:424-430 vs 287-296. `_passes` re-derives fit_sgd's own `examples` counter; the only assertion uses n = 64, where `min(256, n - offset)` is n. A mutation to `min(256, n) * steps` (exactly the v3 4,915,200 error the prereg corrected) passes FitTests. Fix: assert the final-checkpoint candidate's passes equal `run.example_passes` (or use it), and add a `_passes(2000, 3200, True) == 800_000` assertion.

**Minor 4 — the bitwise-checkpoint test has one batch per cycle.** tests/test_m0_fit.py:207-223. With n = 64, `ceil(n/256) = 1`, so every step redraws the permutation; the mid-cycle offset is never crossed by a checkpoint. Production is safe by construction (checkpoint code touches neither `draws` nor `order`; and 200, 800, 3,200, 400, 1,600, 6,400 are all multiples of 8, so they fall on cycle boundaries for n = 2,000), but the test would not catch a checkpoint-induced offset reset. Fix: use n > 256 (e.g. 600) with a checkpoint off the cycle boundary.

**Minor 5 — init draws for h = 8, M-exp and the cold affine start are not byte-pinned.** fit.py:62-80, 275-276. WIDE_SHAS/FIT_SHAS pin the 2-tensor and h = 64 kinds; for the other kinds only shapes and counts are checked, and `test_affine_fit_updates_without_tanh` uses a warm start, so a change that cold-started M-aff from zeros (not N(0, 1e-3)) would pass. Fix: assert the cold affine run's step-0 adapter equals `initial_adapter(seed, nonlinear=False, ...)`, or pin one tensor SHA per kind.

**Minor 6 — the 3-tensor `Adapter.apply` ignores `nonlinear`.** fit.py:34-37. `adapter_shapes` refuses affine M-exp, so no production path reaches it, but a hand-built `Adapter((w1, w2, b), nonlinear=False)` would silently apply tanh. Fix: raise in `apply` when a 3- or 4-tensor adapter has `nonlinear=False`.

Not findings (noted for the controller): wall time booked once on the final-checkpoint candidate is an implementation convention consistent with `m0/worker.py:571-581`; each warm-started rate recomputes the same step-0 selection loss (three identical evaluations, cost only); R-all's "never plateau-certified" rule is enforced, if at all, in `m0/retune.py` (another item), not here. No extra arms, no additional RNG consumption, no change in Gate 3 RNG order or receipt bytes found.
