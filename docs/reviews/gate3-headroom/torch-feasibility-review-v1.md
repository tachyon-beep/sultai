## BLOCKING

### B1. The repo's typing/policy gate does not cover `src/sultai_screen/` at all (§11)
- Claim: "the repo's policy applies" to the new package is false as written.
- Evidence: `scripts/check_policy.py` line `sources = sorted((root / "src/sultai").rglob("*.py"))`; `scripts/check_quality.py` runs mypy on `"src/sultai"` and hashes `(root/"src"/"sultai").glob("*.py")` (non-recursive). A sibling package is invisible to both; the mutation controls also only mutate `sultai/repair.py`.
- Why it matters: every typing claim in §11 would be unverifiable; the preregistration would record a gate that never ran.
- Fix: make this an owner decision with two honest options: (a) widen both scripts to a list of roots (a change to the frozen gate scripts, which must itself be reviewed and have its negative controls extended), adding `sultai_screen` to `[tool.ruff.lint.isort].known-first-party`; or (b) put the package at `src/sultai/screen/` behind a lazy torch import so the stdlib instrument stays import-clean. Also note `check_quality` uses a fresh mypy cache every run and a hardcoded 60 s subprocess timeout; cold mypy on a 60-line file importing torch measured 13.7 s wall / 750 MB RSS here. A real package will likely be 20-40 s, so the timeout is tight but probably survivable; the gate must be timed in the pilot.

### B2. Arm A7 / verdict V2 is decided by inspection, not by experiment
- Claim: the existing former structurally cannot come within Z = 0.01 nat of A2 on any P1-P3 case, so V2 as written is a foregone "does not transfer".
- Evidence: `src/sultai/formation.py` `FrozenGenerator.form` computes 4 coefficients from 6 or 10 pooled moments (`conditioning_evidence`) and `materialize` returns a combination of exactly four fixed templates (`public_templates`: uniform diagonal, cyclic shift, alternating shift-2, alternating +-1 bias). P1's inverse is a non-uniform diagonal (4 of 16 channels), P2's is a dense 16x16, P3's is an arbitrary bias vector: none lies in that 4-D span. Second mismatch: the evidence moments are means of z and tanh(z) with z post-ReLU (>= 0), while the former was fit on h ~ U(-2, 2).
- Why it matters: A7's cost is trivial, but reporting V2 as a transfer test is misleading.
- Fix: either drop V2, or redefine the fair comparator as a 4-coefficient ridge in the same template span (then V2 asks "does the former match its own best-in-class on real activations", which is answerable). On the mapping itself: the per-position pair extraction is faithful (the module is per-position), but 4,096 pairs is already more than enough because `form` consumes only 10 averaged moments; stratify 4 positions per image across 1,024 class-balanced images rather than a uniform draw over 262,144, and generate `Example(sample_id=f"{image}:{y}:{x}", ...)` directly as tuples. Do not materialise 262,144 `Example` objects (each runs `numeric_vector` validation in pure Python).

### B3. Hard rule 5 is incomplete and will raise on the first `Linear` layer
- Claim: `use_deterministic_algorithms(True)` + cuDNN deterministic is not a complete determinism contract on CUDA.
- Evidence: the torch 2.9.1 docstring (printed) states `torch.mm/mv/bmm` raise `RuntimeError` under deterministic mode unless `CUBLAS_WORKSPACE_CONFIG=:4096:8` or `:16:8` is set before CUDA init; the host's `Linear 128->10` and the module's 16x16 per-position matmul hit this. Simic's `enable_class1` (kernel_demo.py ~line 920) sets the env var, `cudnn.benchmark=False`, and disables both TF32 flags (Ada defaults `cudnn.allow_tf32=True`, which changes conv numerics and must be part of the replay contract). Simic requires it to be the first statement of every process.
- Fix: write the full flag set into rule 5 (env var before any CUDA init, deterministic algorithms, cudnn.deterministic, cudnn.benchmark off, TF32 off for both backends, no torch.compile, no AMP, no channels_last), and record all of them in every result file. Note Simic's version uses `os.environ.get`, which `check_policy.py` bans; write it with `in` / `[]`.

### B4. The split derivation as written in §3 is not Simic's derivation
- Claim: `seed = sha256(20261004 || "cifar-fit-dev-v1")[:8]` under-specifies the encoding; a builder following it literally will produce a different permutation.
- Evidence: Simic's `derive` (kernel_demo.py ~line 104) hashes `seed.to_bytes(8, "big")`, then for each label `len(label).to_bytes(4, "big") + label.encode()`, and takes `int.from_bytes(digest[:8], "big")`. I reproduced it on CPU: seed = 6798730733443669431 (63 bits, valid for `manual_seed`); `torch.randperm(50000)` begins `[17416, 42096, 29166, 33200, 42989, 19545, 24596, 13704]`; SHA-256 over the full permutation's int64 little-endian bytes = `df1d87871f9afe3b15d7c5a434c31c5f68ff99564b4512410cc64fb1d042a24e`. The naive concatenation gives a different seed (verified). These are reviewer-measured on CPU torch 2.9.1 and not yet checked against a Simic artifact.
- Also: bounded_data uses `fit = perm[:train_size]`, `dev = perm[45000:45000+dev_size]` with RunSpec defaults 128/64; the draft's "first 45,000 / last 5,000" is the full case and should say so. The draft says the index hash is "checked against Simic's own loader"; importing Simic's loader pulls torchvision and Simic's module side effects. Compare against a saved Simic provenance JSON (`fit_indices`/`dev_indices` in `load_fit_dev`) instead, and note that Simic's `data_split_id` hashes a different split ("valsplit", length-prefixed), so the draft must name the exact bytes it hashes (dtype int64, little-endian, no prefix).
- Fix: write the encoding out, pin the expected seed and permutation SHA in the document after one read-only check, and commit the permutation bytes (int32, 200 KB, or just the 5,000 dev indices) as the source of truth with the derivation as a cross-check. PyTorch gives no cross-version stability guarantee for `randperm`; the small-n CPU path (32-bit `random()` modulo swap for n < 2^32/20) has been stable across 2.x in practice, but only a committed artifact makes the split independent of torch.

## NON-BLOCKING, ordered by consequence

### N1. Cost ledger (§8): host line is plausible-optimistic; oracle line is unverifiable; B5 is missing
- Host: 40,000/32 = 1,250 steps/epoch, 12,500 steps/host. Forward ~37.5M MACs/image (dominated by the 32->32 conv at 32x32 and 64->64 at 16x16; parameter count checks out at ~0.284M including BN affines), fwd+bwd ~220 MFLOP/image, ~90 TFLOP/host = ~15 s if FLOP-bound. It is not FLOP-bound at batch 32: each step is ~100-200 kernel launches (7 convs x 3 kernels, 7 BN x 2, pools, loss, foreach SGD, zero_grad, the on-GPU augment gather with its index tensors, and `fill_uninitialized_memory` kernels on every `torch.empty` under deterministic mode), i.e. Python/launch-bound at ~4-10 ms/step depending on per-step `float()` syncs. My estimate: 50-130 s/host; the draft's 60-90 s is the optimistic edge. If Simic's `train_one_epoch` is copied, its per-parameter `float(p.grad.pow(2).sum())` per step adds ~30 device syncs per step; do not copy that. Branch accounting overcounts ~20% (anchor = 3 epochs, branch = 7).
- Oracle: "schedule 1x / 4x" has no step count, batch size or stopping rule, and "plateau certified" is undefined, so 2-4 s/fit cannot be checked. With z cached once per host (conditioning 2,000 x 4,096 fp32 = 33 MB; selection 49 MB; dev 82 MB), a full-batch step over 2,000 examples through the downstream (input-grads only, host params frozen) is ~50-100 ms, so 2-4 s is 20-80 full-batch steps; minibatch schedules are launch-bound at ~5 ms/step. My B3 estimate: 1x ~2.5 s, 4x ~10 s, grid of 24 ~150 s per host-case, 128 host-cases ~4.5-5.5 GPU-h single-stream, above the ledger's 2-4.
- Missing dominant item: B5 (16->64->16 oracle) has no ledger line; on the full B3 grid it duplicates the dominant term (+4-5 GPU-h). B4's Hungarian alignment is trivial at n=16 but needs an implementation (no scipy in the proposed dependency group).
- My totals: hosts 2-3 GPU-h, B3 4.5-5.5, A6 0.35, cheap arms + evaluations 0.5, B5 0 or 4-5: ~8-9 GPU-h without B5, ~12-13 with, single-stream. The proposed 10 GPU-h confirmatory ceiling needs B5 reduced (e.g., 1 seed x 2 lr x 1x on 8 anchors) or the ceiling raised. Pilot as specified (4+2 anchors, full B3 grid on 24 host-cases) is ~1.5-2 GPU-h single-stream, above the proposed 1 GPU-h pilot ceiling unless concurrency is used.
- Concurrency: because everything except full-batch oracle steps is launch-bound, 3-4 independent processes per card (each pinned by `CUDA_VISIBLE_DEVICES`, each asserting `device_count()==1`) should give ~2-3x aggregate throughput; wall on two cards ~3-4 h. Determinism per process is unaffected unless cuDNN workspace allocation fails, which is nil at <1 GB/process; still replay under the same co-tenancy in the pilot. Set `torch.set_num_threads(1 or 2)` per process.

### N2. BatchNorm: "downstream BN eval" is necessary, not sufficient
- The producer/stem BN must also be in eval when z is extracted, or z depends on batch composition and on how many batches have passed; z should be computed once per host under `host.eval()` + `torch.no_grad()` and cached. All host parameters need `requires_grad_(False)` (BN affines included) so backward only computes input grads.
- Robust test: (1) a forward hook on every `_BatchNorm` in the host asserting `not module.training` during every fit and evaluation; (2) a SHA-256 over `named_parameters()` and `named_buffers()` (typed iterators; covers `running_mean/var/num_batches_tracked`) before and after every fit/eval, asserting identity, which catches a stray `.train()` the hook misses; (3) a negative control that deliberately sets train mode and shows the test fails, per the repo's control convention; (4) after a fit, assert `p.grad is None` for every host parameter.
- Trained-through bottleneck: if the 1x1 16->4->16 block contains BN/ReLU it sits in the frozen path and is covered by the same hash. A builder gap: for P6 (read z, write after the bottleneck) the module `u = z + (W tanh z + b)` at init reproduces z, not z-tilde, so the SGD arms B1/B2 start from a bypass, not from the no-op; the draft must state B0 for P6 and the residual base of the module (z or z-tilde).
- Useful known-answer: with W=0, b=0 the module is bitwise identity, so no-op must equal the unmodified host exactly.

### N3. Determinism: the recipe should replay bitwise; two documented offenders need a stated workaround
- The printed 2.9.1 throw list includes `AdaptiveAvgPool2d` backward on CUDA and `NLLLoss` on CUDA. Simic uses `nn.AdaptiveAvgPool2d(1)` and `cross_entropy` under the same flags and is running on these cards now, consistent with the 1x1 fast path to `mean` and the alert living in the 2-D NLL kernel; but write GAP as `x.mean(dim=(2, 3))` so the document does not rely on an undocumented special case. `F.pad(mode="reflect")` is fine only because augment runs without grad; keep it that way. `max_pool2d` backward is deterministic for contiguous NCHW; do not use channels_last.
- Host init draws from the global CPU RNG inside `reset_parameters`; rule 4 ("all generators are CPU generators seeded by derivation") is only true if construction happens inside Simic's `rng_scope` pattern or after an explicit derived `torch.manual_seed`. The spawn checkpoint must include optimizer momentum buffers and the pre-drawn future (order/crops/flips), or branches cannot replay.
- Pilot should test: (i) one fwd/bwd of the exact host on a 2-image batch under the full flag set (catches every raise in seconds); (ii) two full anchor trainings in separate processes on the same card comparing a per-epoch hash over params+buffers and the per-step loss stream, not only the final loss; (iii) the same on the other card (same SKU) so a card failure does not void replay; (iv) one oracle fit replay, since full-batch reductions use different kernel configs than batch 32; (v) replay under the confirmatory co-tenancy.

### N4. Data sealing is enforceable; prefer an audit hook plus a hand-rolled loader
- Verified here: `sys.addaudithook` raising on `open`/`os.open` events whose path contains `test_batch` catches `builtins.open`, `os.open`, `io.open` and `Path.read_bytes`, while leaving `data_batch_1` readable. Install the hook at process start in sealed-run mode (not only in tests), count the five `data_batch_*` opens, record both in the result file, and add the negative control (hook fires when test_batch is opened).
- torchvision is not in the proposed dependency group and its stock `CIFAR10(train=True)` opens `test_batch` in `_check_integrity` (Simic had to subclass around it); use a five-file pickle loader after per-file SHA-256 verification, wrapped as a T3 boundary. Verify the five extracted files and `batches.meta` individually; do not verify the archive, since hashing the tarball reads test_batch bytes.

### N5. Strict typing: feasible with zero or one exemption if the right idioms are used
- What the gate enforces (measured under the repo's exact config): `disallow_any_explicit` and the AST ban are lexical on `Any`/`cast`/ignores; implicit Any from torch's inline types is allowed to flow. Leaks found: `nn.Module.__call__` returns Any; `state_dict()` is `dict[str, Any]`; `.tolist()` Any; `torch.load` Any; `opt.param_groups` `list[dict[str, Any]]`; `.numpy()` is `ndarray[tuple[Any,...], dtype[Any]]`. Errors found: `loss.backward()` is a `no-untyped-call`; `torch.backends.cudnn.version()` is a `no-untyped-call`; `warn_return_any` fires on `return self.fc(h)`, which is why Simic uses `cast` (banned here).
- Patterns that pass (verified): `torch.autograd.backward(loss)` or `torch.autograd.grad(loss, [W, b])` (typed `tuple[Tensor, ...]`, and the oracle wants grads only for W, b anyway); bind module outputs to an annotated local `y: torch.Tensor = layer(x)` before returning, or call `layer.forward(x)` on leaf layers (typed, but bypasses hooks, so not on BN if the hook assertion is used); `isinstance(out, torch.Tensor)` narrowing where a runtime check is wanted; hash via `named_parameters()`/`named_buffers()` not `state_dict()`; `.numpy().tobytes()` inline (typed `bytes`), never `.tolist()`; `torch.load(weights_only=True)` typed as `object` through a `@t3_boundary` with a paired test; CIFAR pickle through the same boundary; `np.ndarray[tuple[int, ...], np.dtype[np.uint8]]` annotations (bare `np.ndarray` fails `disallow_any_generics`). Oracle non-convergence needs its own specific T2 failure class (the gate rejects `ValueError`/`ContractViolation` in `failures`).
- The honest residual exemption: recording the cuDNN version (`no-untyped-call`); either accept one documented exemption or record `torch.version.cuda` and the wheel string only. The annotated-local idiom is a silent narrowing the gate cannot see; the preregistration should say whether it counts as an escape and, if so, require the runtime-checked helper.

### N6. Two instrument-numerics points the builder will hit
- "A1 restores intact loss within the twin noise floor": a no-op twin on a resampled evaluation order measures float summation order (~1e-7 nat), not sampling noise, so the floor is near zero; A1 in fp32 (0.1 is not representable; a s_min = 0.1 mixing inverted in fp32 loses ~1e-6 relative) will not be within it. Give A1 an explicit tolerance (e.g., 1e-4 nat) and leave the twin-floor redesign to the Astra review.
- A1 is an operator, not a member of the 272 module family, and the tanh template cannot express a linear inverse on post-ReLU z (tanh saturates above ~2), so A2 (tanh ridge) will not reach A1 on P1/P2 by construction; the affine control A3 is the arm that can. Worth stating so V0 is not misread.

### N7. §11 structure
- Record Simic's recipe now rather than at the pilot: lr 0.05 constant (no scheduler), momentum 0.9, nesterov, weight decay 5e-4 with `ndim <= 1` params excluded, batch 32 via `RunSpec`, CIFAR mean/std (0.4914, 0.4822, 0.4465)/(0.2470, 0.2435, 0.2616), reflect-pad-4 random crop + p=0.5 flip with all draws made up front on CPU, whole uint8 dataset resident on GPU (154 MB).
- `host.py` should expose the cached-z path (upstream eval/no_grad once, downstream-only fit/eval) as the primary interface; "site hooks" are the wrong abstraction for a frozen-downstream oracle and complicate typing.
- `pyproject` extras: `torch==2.9.1` resolves to the CPU wheel from PyPI by default; the measured build is `+cu128` from the PyTorch index. Record the full wheel string and index in the document.
- Memory: peak per process well under 1 GB (CUDA context ~300-500 MB, dataset 154 MB, batch-32 activations negligible, full-batch oracle over 2,000 cached z ~1.2 GB worst case); 16 GB is not a constraint. `CUBLAS_WORKSPACE_CONFIG=:4096:8` reserves 32 MB per handle.
